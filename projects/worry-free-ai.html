01 / OVERVIEW

서비스를 만들고, 운영하며 개선했습니다

걱정마AI는 네이버 플레이스 키워드별 매장 순위와 관련 데이터를 분석하고, 블로그 콘텐츠 생성 및 발행을 자동화하는 서비스입니다.

기획 전담 인력이 없는 소규모 팀에서 백엔드 상급자와 협업하며 초기 기획, ERD 설계, API 개발부터 실제 유료 사용자 대상 서비스 운영까지 참여했습니다. 운영 과정에서 데이터 수집 효율, 자동화 작업의 실패 처리, 코드 구조를 지속적으로 개선했습니다.

인증 및 상용 서비스 기능

  • JWT 기반 회원가입·로그인 및 권한 관리
  • Kakao OAuth 연동
  • Toss Payments 결제 API 연동 및 이용권 정보 관리
  • 관리자 페이지용 API

플레이스 데이터 수집

  • 키워드·placeId 기반 순위, 리뷰 수, 검색량, 경쟁도 조회
  • 일 단위 순위 및 월 단위 검색량 수집 이력 관리
  • 유효기간에 따른 기존 DB 조회 및 외부 수집 요청
  • 사용자 등록 키워드 우선 수집 및 신규 키워드 즉시 수집

블로그 자동화

  • OpenAI API 기반 콘텐츠 생성
  • Python·Playwright 기반 블로그 발행 자동화
  • 단계별 진행 상태, 실패 사유 기록 및 재시도 기능

02 / ENGINEERING

수집 속도와 수집 정책을 함께 개선하다

문제

초기에는 Playwright와 Selenium 기반 브라우저 자동화로 네이버 플레이스 데이터를 수집했습니다. 두 개의 크롤러를 동시에 실행해도 24시간 안에 필요한 키워드를 모두 수집하지 못했습니다.

분석 및 개선

실제 서비스의 네트워크 요청을 분석해 GraphQL 요청 구조를 파악하고, 이를 활용하는 데이터 수집 방식으로 개선했습니다. 동시에 모든 데이터를 동일한 주기로 수집할 필요가 없다는 점에 주목했습니다.

순위 데이터
매일 수집
가게 상세 정보
2주 간격으로 수집
사용자 등록 키워드
우선 수집
신규 키워드
별도 흐름으로 즉시 수집
기존 데이터
유효기간 확인 후 재사용

결과

기존에는 24시간 수집해도 필요한 데이터를 모두 처리하지 못했지만, 개선 후에는 더 많은 키워드를 약 3~4시간 안에 수집할 수 있게 되었습니다.

GraphQL 요청 방식 변경과 수집 주기·우선순위 조정 등이 함께 기여한 결과입니다. 동일 조건의 벤치마크나 특정 기술 하나의 개선율로 해석하지 않습니다.

수집 성능은 실행 속도뿐 아니라 데이터 변경 주기, 중요도, 기존 데이터 재사용 정책까지 함께 설계해야 한다는 점을 배웠습니다.

보완 예정: 외부 서비스 요청 제한 및 인터페이스 변경에 대응한 구체적인 사례는 확인 후 추가합니다.

03 / ENGINEERING

RabbitMQ로 작업 요청과 수집 실행을 분리하다

문제와 선택

수집 대상 조회, 작업 실행, 결과 저장을 하나의 동기 흐름으로 연결하면 작업 관리와 확장에 한계가 있었습니다. RabbitMQ를 이용해 작업 요청과 크롤러 실행을 분리하고 작업 종류별 큐로 라우팅했습니다.

운영 방식

수집 실패는 드물게 발생했고, 주로 유효하지 않은 키워드 등이 원인이었습니다. 별도의 자동 장애 복구 시스템을 구축하지 않았으며, 매일 아침 로그와 실패 작업을 확인하고 필요한 경우 수정하는 방식으로 대응했습니다.

배운 점

비동기 처리는 큐에 작업을 넣는 것으로 끝나지 않습니다. 작업 상태 관리, 결과 전달과 운영 중 오류 확인까지 함께 고려해야 한다는 점을 경험했습니다.

04 / ENGINEERING

블로그 발행 실패를 단계별로 확인하고 재시도하다

초기 문제

블로그 발행 기능을 동기식으로 구현하여 중간에 실패하면 사용자에게 오류 원인이 충분히 전달되지 않았고, 작업을 처음부터 다시 실행해야 했습니다.

개선

각 단계의 성공·실패 상태와 실패 사유를 기록하여 사용자에게 현재 상황과 필요한 조치를 안내했습니다. 조치 후에는 이전에 완료한 작업을 불필요하게 반복하지 않고 다시 진행할 수 있도록 구현했습니다.

결과

사용자가 진행 상황과 오류 원인을 확인할 수 있게 되었으며, 계정 문제처럼 사용자 측 조치가 필요한 상황을 구분해 대응할 수 있게 되었습니다.

05 / ENGINEERING

데이터 특성에 맞춰 조회와 갱신 정책을 나누다

문제

키워드별 플레이스 데이터가 누적되면서 동일한 데이터를 반복 조회하거나 외부 수집 요청을 다시 수행하는 비용을 줄일 필요가 있었습니다.

개선

crawling, place-ranks, reviews 등 데이터 성격에 따라 저장 구조를 분리하고 placeId를 중심으로 업체를 식별했습니다.

  • 순위는 일 단위, 검색량은 월 단위 수집 이력 확인
  • 사용자가 지정한 키워드와 placeId 기준으로 최근 2주 순위 조회 쿼리 구현
  • 여러 키워드의 순위 정보를 확인할 수 있는 조건별 조회 지원
  • 수집 성공·실패 상태를 활용해 재수집 여부 판단

결과

기존 데이터로 응답할 수 있는 경우 반복 외부 요청을 줄이고, 데이터 특성에 맞는 갱신 정책을 적용했습니다.

조회 응답 시간의 개선 수치는 별도로 측정하지 않았습니다. 별도 집계 테이블을 통한 전체 데이터 사전 계산을 구현한 것으로 설명하지 않습니다.

06 / ENGINEERING

멀티모듈 구조로 책임을 분리하다

문제와 개선

서비스 계층에 여러 도메인의 업무 로직이 집중되면서 코드의 책임과 외부 연동 위치를 파악하기 어려워졌습니다. core, api, admin, scheduler, infra 모듈로 구조를 분리하고, UseCase 중심으로 업무 흐름을 조합했습니다.

Controller
HTTP 요청 및 응답 처리
UseCase
조회·수집·저장 등 업무 흐름 조합
Infra
크롤러 HTTP 연동, RabbitMQ, Redis
Core
공통 엔티티 및 enum 등 공유 모델

설계상 한계와 개선 방향

관심사 분리와 일부 헥사고날 아키텍처 원칙을 참고했지만, 현재 구조는 책임 분리를 적용한 멀티모듈 계층형 구조에 가깝습니다.

UseCase가 외부 연동 구현체를 직접 참조하는 부분이 있고, core 엔티티도 JPA 어노테이션에 의존합니다. 앞으로 개선할 지점은 이러한 직접 의존의 변경 영향을 살펴보고 필요한 경계를 분리하는 것입니다.

패턴의 이름보다 실제 의존성 방향과 변경 영향을 관리하는 것이 중요하다는 점을 배웠습니다.

07 / OPERATIONS & REFLECTION

사용자 피드백을 다음 개선으로 연결하다

사용자 피드백과 운영

  • 키워드 선정의 어려움을 해결하기 위한 키워드 추천 기능 개발
  • 블로그 발행 오류에서 서비스 내부 문제와 사용자 계정 문제를 구분하여 원인 안내
  • 사용자 요청의 필요성과 서비스 전체 영향도를 검토해 개선 우선순위 결정

운영을 통해 기능 구현뿐 아니라 장애 대응, 외부 서비스 변경, 사용자 지원에도 상당한 리소스가 필요하다는 점을 경험했습니다.

프로젝트 성과

  • 초기 설계부터 상용 서비스 개발·운영까지 참여
  • 실제 유료 사용자 대상 서비스 운영 및 피드백 반영
  • 데이터 수집 구조 개선으로 더 많은 키워드를 약 3~4시간 내 수집
  • 2026년 스마트상점 기술보급사업 선정 서비스의 기술 개발 참여

사업 신청과 대외 업무는 대표자가 담당했으며, 서비스의 기술 개발은 본인과 백엔드 상급자가 함께 수행했습니다.
