01 / OVERVIEW

베이킹 공간의 예약부터 재료 정산까지

에브리키친은 베이킹 공간의 예약, 전문 설비 정보 제공, 재료비 정산을 지원하는 공유주방 대여 플랫폼입니다. 일반 공유주방과 달리 오븐·반죽기·조리 도구·식재료를 함께 관리해야 하는 베이킹 공간의 요구에 착안해 기획했습니다.

4인 팀의 팀장으로서 기획, 일정 관리, 개발 환경 구성, ERD·API 명세 설계와 주요 기능 구현, 배포를 주도했습니다.

공간 관리

  • 호스트의 주방 등록·수정·삭제
  • 주방별 예약 가능 시간대 설정
  • 설비·도구·구비품·식재료 정보 관리
  • 주방 검색·필터링 및 이미지 업로드

예약 및 결제

  • 예약 상태에 따른 흐름 관리
  • KakaoPay 예약 이용료 결제
  • 결제 전·후 취소 규칙 구분

이용 후 정산

  • 호스트가 재료별 단가 등록
  • 이용자가 실제 재료 사용량 입력
  • 단가와 수량을 바탕으로 추가 비용 계산

02 / CORE ENGINEERING

Redis TTL로 예약 시간대를 잠시 선점하다

문제

주방은 같은 시간대에 여러 사용자가 동시에 이용할 수 없습니다. 예약 요청 뒤 결제하지 않는 사용자가 예약 시간을 무기한 점유하지 않도록 결제 대기 시간을 제한해야 했습니다.

구현 흐름

사용자가 주방과 시간대를 선택하면 Redis에서 기존 선점 정보를 확인하고, 값이 없을 때 예약 정보를 저장하면서 TTL을 10분으로 설정했습니다. 예약 정보를 별도의 스케줄러로 만료시키는 방식은 사용하지 않았습니다.

현재 구현의 한계

실제 구현에서는 Redis의 기존 값을 조회한 뒤 선점 값을 저장하는 작업을 별도로 수행했습니다. 따라서 일반적인 중복 예약을 제한하는 효과는 있지만, 두 요청이 동시에 조회와 저장 사이에 진입하는 경우까지 원자적 선점을 보장하지는 않습니다.

개선 과제 · 실제 구현 완료가 아닙니다

  • SET NX EX 또는 setIfAbsent와 TTL로 확인·저장을 원자적으로 처리
  • 결제 확정 시 영구 예약 데이터의 중복 여부 재검증
  • 선점 만료와 결제 완료가 경합할 때 Redis·DB 상태 정합성 검토

03 / CORE ENGINEERING

이용 후 실제 재료 사용량을 정산하다

문제

베이킹 공간은 이용자가 예약할 때 실제 재료 사용량을 확정하기 어렵습니다. 예약 시점에 모든 재료비를 고정하면 사용량 차이를 반영하기 어렵다는 점이 있었습니다.

해결

호스트가 주방에서 제공하는 재료의 단가를 등록하고, 이용자가 사용 후 실제 수량을 입력하면 단가와 수량을 바탕으로 추가 비용을 계산하도록 구현했습니다.

배운 점

공간 이용료와 사용 후 확정되는 재료비를 별도 시점에 다루면서, 결제 흐름이 도메인의 실제 사용 과정과 맞물리도록 설계하는 경험을 했습니다.

04 / DELIVERY

Docker 이미지로 프론트엔드와 백엔드를 함께 배포하다

기존 방식의 불편

초기에는 프론트엔드와 백엔드를 별도로 배포했습니다. 개발 후반에 수정이 잦아지면서 두 구성요소를 따로 배포하는 과정이 번거로워졌습니다.

변경

프론트엔드와 백엔드를 Docker 이미지로 구성하고 AWS EC2에서 이미지를 가져와 함께 실행하는 통합 배포 방식으로 변경했습니다. 두 구성요소는 공유 데이터베이스를 사용했습니다.

GitHub Actions·Jenkins 기반 자동 배포는 적용하지 않았으며, Docker Compose 사용 여부도 확인되지 않아 기재하지 않았습니다. 배포 시간이나 다운타임 개선 수치는 측정되지 않았습니다.
