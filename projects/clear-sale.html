01 / OVERVIEW

미분양 매물과 상담을 연결하는 플랫폼

클리어분양은 미분양 매물의 정보 접근성을 높이고 일반 고객과 분양사의 상담 연결을 지원하기 위해 개발한 플랫폼입니다. 고객은 매물과 할인 혜택을 확인하고 상담을 요청하며, 분양사는 매물을 등록하고 상담 요청을 관리할 수 있도록 설계했습니다.

기업에서 제공한 RFP를 바탕으로 16명이 협업했습니다. 백엔드 팀장으로 초기 설계와 기술 구현, 개발 환경 구성, 직군 간 협업 및 최종 발표에 참여했습니다.

인증 및 권한 관리

  • Spring Security·JWT 기반 회원 인증
  • ADMIN·MEMBER 역할별 API 접근 제어
  • Redis에 Refresh Token 저장
  • 이메일·SMS 인증 정보 관리

매물 및 상담

  • 미분양 매물 CRUD, 검색·필터링
  • 이미지 업로드
  • 상담 요청 및 담당자 배정
  • Redisson 기반 상담 배정 동시성 제어

데이터 및 인프라

  • AWS RDS(MySQL) 영구 저장
  • AWS S3 Presigned URL 업로드
  • Redis 임시 데이터 관리
  • Nginx 리버스 프록시
  • Grafana 대시보드·Discord 알림 활용

02 / TROUBLESHOOTING

Redisson 분산 락으로 상담 중복 배정을 막다

문제

하나의 상담 요청에 여러 상담사가 동시에 담당자로 지정하려는 상황에서 동일 상담 건이 중복 배정될 가능성이 있었습니다. 애플리케이션 인스턴스 내부의 동기화만으로는 여러 인스턴스가 공유하는 상담 상태를 함께 보호할 수 없어 분산 락을 적용했습니다.

구현 중 발견한 문제

01 · k6 응답 상태 코드

증상

오류 상황인데 HTTP 응답 코드가 200으로 전달되어 테스트에서 성공 응답과 구분하기 어려웠습니다.

확인 및 조치

오류 코드의 HTTP 상태 매핑을 HttpStatus.BAD_REQUEST.value()로 변경했습니다.

결과

오류 응답을 HTTP 상태 코드로 구별할 수 있게 됐습니다. 이 조치는 오류 응답 의미를 바로잡은 것이며, 분산 락 처리량 개선 수치로 해석하지 않습니다.

02 · HikariCP 커넥션 부족

증상

동시성 테스트 중 Connection is not available 오류가 발생했습니다.

확인 및 조치

락 대기 시간과 임대 시간 설정을 조정했습니다.

결과

락 대기와 커넥션 사용이 맞물리는 상황을 확인하고 설정을 조정했습니다. 정량 처리량이나 성공률 수치는 측정 자료가 없어 제시하지 않습니다.

03 · 불필요한 분리 트랜잭션

증상

락 획득 실패 처리에 별도의 분리 트랜잭션이 사용되고 있었습니다.

확인 및 조치

락 획득 실패 경로에서 필요하지 않은 분리 트랜잭션을 제거했습니다.

결과

실패 처리에 필요하지 않은 트랜잭션 경로를 줄였습니다. 별도의 성능 개선 수치는 확인되지 않았습니다.

결과와 배운 점

동일 상담 건의 담당자 지정 구간을 분산 락으로 보호하고, 테스트 중 드러난 HTTP 오류 매핑·커넥션 대기·불필요한 트랜잭션 문제를 각각 조정했습니다. 동시성은 락 자체뿐 아니라 트랜잭션과 DB 커넥션 사용까지 함께 살펴야 한다는 점을 배웠습니다.

03 / AUTHENTICATION

Spring Security와 JWT 인증·인가

STATELESS 세션 정책의 SecurityFilterChain을 구성하고 BCrypt로 비밀번호를 검증했습니다. Access Token과 Refresh Token은 서명 키를 분리해 발급했으며, HS256 JWT에 이메일·역할·발급 시각·만료 시각을 담았습니다.

컨트롤러에서는 @AuthenticationPrincipal로 인증된 사용자 정보를 전달받았습니다.

개선 과제 · 구현 완료 항목이 아닙니다

  • 토큰 재발급 API에서 토큰 전달 경로 명확화
  • 로그아웃 시 Redis Refresh Token 삭제
  • 인증 실패 응답 형식 통일
  • 로그에서 토큰 원문 제거

04 / AWS & DATA

영구 데이터와 파일 저장 인프라 구성

AWS RDS · MySQL

회원, 매물, 상담 등 영구 데이터를 저장하도록 직접 구성하고 운영했습니다.

Redis

Refresh Token, 이메일·SMS 인증 정보, 관심 매물 임시 데이터와 Redisson 분산 락에 활용했습니다. 직접 구성하고 운영했습니다.

AWS S3

매물 이미지와 관련 파일 저장에 사용했습니다. 백엔드가 Presigned URL을 발급하고 클라이언트가 S3에 직접 업로드합니다.

05 / TEAM LEADERSHIP

RFP를 구체적인 백엔드 작업으로 나누다

기업은 고객 유입 이전에 미분양 매물의 기초 데이터를 확보하는 것을 중요하게 생각했고, 관리자 기능의 우선 개발을 요청했습니다. 지방 미분양 매물과 정보의 투명성도 논의했습니다.

프로젝트 초기에 ERD와 Swagger API 명세를 작성하고, PM과 개발 우선순위를 협의했습니다. 전체 일정 관리는 PM이 맡았고, 저는 백엔드 구현과 팀 협업을 이끌었습니다.

백엔드 팀장 역할

  • 백엔드 5명 역할 분담 및 공통 개발 환경 구성
  • ERD 및 Swagger API 명세 작성 주도
  • Git 브랜치 전략 협의 및 오프라인 협업 활성화
  • PM과 요구사항·우선순위 조율
  • 타 직군과 구현 조건을 맞추고 최종 발표 진행

06 / COLLABORATION

요구사항을 다시 확인하고 구현 방향을 맞추다

문제

일부 요구사항이 PM에서 다른 직군으로 전달되는 과정에서 다르게 이해되어 구현 방향에 혼선이 생겼습니다.

해결

먼저 UX/UI와 프론트엔드 팀원들과 실제 요구사항을 확인했습니다. 이후 해당 PM과 약 30분간 논의해 전달 과정의 차이를 정리하고 개발 방향을 합의했습니다.

배운 점

기술 구현뿐 아니라 여러 직군이 같은 요구사항을 이해하도록 확인하고 조율하는 과정이 중요하다는 점을 경험했습니다.

07 / DELIVERY & REFLECTION

배포 환경을 시연하고 프로젝트를 마무리하다

배포와 모니터링

Nginx 리버스 프록시 환경에서 서비스를 구동했습니다. 다른 구성원이 설정한 Grafana 대시보드와 Discord 봇 알림을 활용해 서비스 상태를 확인했습니다.

초기 배포 때 CORS 등 환경 설정 문제를 경험하고 해결했지만, 구체적인 원인과 수정 방법은 확인되지 않아 상세 내용은 덧붙이지 않습니다. 무중단 배포를 구현한 것으로 설명하지 않습니다.

프로젝트 성과

  • 기업 RFP의 필수 기능 구현 완료
  • 배포 환경에서 서비스 구동 및 기업 담당자 대상 최종 시연·발표
  • 개발자 출신 기업 대표를 포함한 담당자로부터 긍정적인 평가 확보
  • 16명 규모 협업 프로젝트에서 백엔드 팀장 역할 수행
  • 인증·인가, 분산 락, AWS 데이터 저장 인프라 구현

프로젝트는 개발 완료 상태이며 현재 운영 중인 서비스는 아닙니다.

회고

클리어분양은 백엔드 개발과 팀 리딩을 함께 경험한 프로젝트입니다. Spring Security와 JWT 인증 구조를 직접 구성하고 Redisson 분산 락을 구현하며 보안과 데이터 일관성을 고려했습니다.

AWS 인프라를 구성하고 배포를 경험했으며, 기업 요구사항을 구체화하고 여러 직군의 의견을 조율하는 과정에서 기술적 책임과 협업의 중요성을 배웠습니다.
